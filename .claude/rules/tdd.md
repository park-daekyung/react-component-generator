# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계 생략, 순서 변경, 예외 임의 추가를 금지한다.

## 우선순위

프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙을 우선**한다. 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 다루지 않는 부분만 이 파일을 따른다.

## 1. 적용 기준

### 반드시 TDD를 적용한다

- 비즈니스 로직
- API (라우트, 외부 API 호출 래퍼, 에러 변환)
- 유틸 함수, 순수 함수
- 버그 수정 (**재현 테스트를 먼저 작성**하고 실패를 확인한 뒤 수정한다)
- 동작이 있는 훅과 상호작용이 있는 컴포넌트

### TDD가 불필요하다

- 타입 정의 (`types/`, `interface`, `type`)
- 설정 파일 (`vite.config.ts`, `tsconfig*.json`, `eslint.config.js`, `package.json`)
- 순수 UI (스타일, 레이아웃, 마크업만 바꾸는 변경)
- SQL, 마이그레이션 스크립트

경계가 모호하면 **TDD를 적용한다.**

## 2. RED-GREEN-REFACTOR

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 검증하지 않는다.
- 테스트 이름은 기대하는 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. import 오류, 문법 오류, 오타, 잘못된 셋업으로 실패했다면 테스트를 고쳐서 올바른 이유로 실패시킨다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트나 기대값을 의심한다.

### GREEN: 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** 원칙을 따른다. 테스트가 요구하지 않는 분기, 옵션, 추상화를 넣지 않는다.
- 실행해서 **신규 테스트와 기존 테스트가 모두 통과**하는지 확인한다.
- 기존 테스트가 깨지면 새 코드를 고친다. 기존 테스트를 수정해서 맞추지 않는다 (요구사항이 실제로 바뀐 경우 제외).

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green을 유지한다.** 변경할 때마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 재시작한다.**

- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 별도 파일 보관, 복사해 두기, 기억해서 다시 쓰기 모두 포함한다.
- 삭제한 코드를 보고 테스트를 맞추지 않는다. 요구사항에서 테스트를 새로 도출한다.

## 4. 변명 차단표

| 변명 | 반론 |
| --- | --- |
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 단순해 보이는 코드가 가장 자주 조용히 깨진다. |
| 나중에 추가하겠다 | 나중에 쓴 테스트는 구현을 베끼므로 버그도 함께 통과시킨다. 그리고 나중은 오지 않는다. |
| 시간이 없다 | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. 시간이 없을수록 테스트가 필요하다. |
| 삭제하면 낭비다 | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 더 크다. 다시 쓰는 것은 빠르다. |
| 프로토타입이다 | 프로토타입은 그대로 제품이 된다. 버릴 코드라고 확신하면 코드를 버려라. 남길 코드라면 테스트부터 써라. |
