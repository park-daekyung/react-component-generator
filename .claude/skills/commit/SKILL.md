# Commit

변경사항을 분석하여 컨벤션에 맞게 커밋하는 스킬이다. 별도 승인을 묻지 않고 바로 커밋한다.

## 절차

### 1. 변경사항 분석

다음 명령으로 현재 상태를 파악한다.

```bash
git status --short
git diff            # 아직 stage하지 않은 변경
git diff --staged   # 이미 stage한 변경
git log --oneline -10   # 기존 커밋 메시지 스타일 확인
```

- 저장소가 아니면(`git rev-parse` 실패) 그 사실을 알리고 중단한다.
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.
- untracked 파일은 내용을 읽어 변경 의도를 파악한다.
- `.env`, 키·토큰이 들어간 파일, `node_modules`, 빌드 산출물은 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눈다.
- 같은 목적의 파일(예: 컴포넌트와 그 스타일, 테스트)은 한 커밋으로 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 주된 목적의 커밋에 함께 묶는다.
- 분류 결과를 "커밋 1: 파일 목록과 한 줄 설명" 형태로 정리한다.

### 3. 커밋 메시지 작성

형식:

```
<타입>: <요약>

<본문(선택)>
```

| 타입 | 용도 |
| --- | --- |
| feat | 사용자에게 보이는 기능 추가나 변경 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 빌드, 설정, 의존성, 문서 등 기타 |

규칙:
- 요약은 한국어, 50자 안팎, 마침표 없이 쓴다. 무엇을 했는지 현재형 명사구나 동사로 쓴다. 예: `feat: 레트로 데스크톱 테마로 전체 UI 개편`
- 본문은 "왜" 바꿨는지가 diff만으로 드러나지 않을 때만 쓴다. 한 줄 72자 안팎으로 줄바꿈한다.
- 기존 `git log`의 스타일이 이 규칙과 다르면 이 스킬의 규칙을 따른다.
- 세션 시스템 안내에 커밋 attribution 줄(Co-Authored-By 등)이 있으면 메시지 끝에 그대로 붙인다.

### 4. 커밋

1. 승인을 기다리지 않고 분류한 커밋 순서대로 바로 진행한다. 진행 전에 커밋 계획(파일 목록과 메시지)을 한 번 출력해 사용자가 볼 수 있게 한다.
2. 커밋별로 파일을 명시해서 stage한다. `git add -A`나 `git add .`는 쓰지 않는다.
3. 메시지는 heredoc으로 전달해 줄바꿈과 한글이 깨지지 않게 한다.

   ```bash
   git add <파일들>
   git commit -m "$(cat <<'EOF'
   feat: 요약

   본문
   EOF
   )"
   ```

4. 커밋마다 `git log --oneline -n <커밋 수>`와 `git status --short`로 결과를 확인하고 보고한다.

## 금지 사항

- 사용자가 요청하지 않으면 `git push`, `--amend`, `--force`, `--no-verify`를 쓰지 않는다.
- pre-commit hook이 실패하면 우회하지 말고 원인을 보고하고 고친다. 고친 뒤에는 amend가 아니라 새 커밋으로 만든다.
- 기본 브랜치(main, master)에 있으면 커밋 전에 새 브랜치를 만들어 그 위에서 커밋한다.
